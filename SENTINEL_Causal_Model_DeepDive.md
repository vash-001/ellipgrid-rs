# النموذج السببي في SENTINEL — شرح كامل من الصفر

> هذه الوثيقة تشرح النموذج السببي وحده — من الفلسفة إلى المعادلات إلى التطبيق.
> لا تحتاج أي خلفية مسبقة في السببية أو Do-Calculus.

---

# الجزء الأول: ما هي السببية؟ ولماذا تختلف عن الارتباط؟

## 1. الفرق بين الارتباط والسببية

هذا هو أهم مفهوم في المشروع بأكمله. إذا فهمته، فهمت لماذا SENTINEL مختلف عن كل شيء آخر.

### الارتباط (Correlation):

```
الملاحظة: "كلما زادت مبيعات المثلجات، زادت حالات الغرق"

هل المثلجات تسبب الغرق؟ ❌ لا!
السبب الحقيقي: الحرارة العالية (confounders)
  → الحرارة تزيد مبيعات المثلجات
  → الحرارة تزيد السباحة → تزيد الغرق

الارتباط يقول: "يحدثان معاً"
ولكنه لا يقول: "أحدهما يسبب الآخر"
```

### السببية (Causation):

```
السببية تقول: "إذا تدخّلت وغيّرت X، هل يتغير Y؟"

اختبار: إذا منعنا بيع المثلجات قسراً (تدخل)
  → هل ينخفض الغرق؟
  → لا! لأن الحرارة لا تزال مرتفعة والناس لا تزال تسبح

إذاً: المثلجات لا تسبب الغرق ← ارتباط فقط، ليس سببية
```

### في الأمن السيبراني — نفس المشكلة بالضبط:

```
┌─────────────────────────────────────────────────────────────┐
│                                                             │
│  الملاحظة:                                                  │
│  "كلما شغّلنا nginx، حدثت قراءة لـ /etc/shadow"            │
│                                                             │
│  النظام التقليدي (ارتباط):                                  │
│  "nginx مرتبط بقراءة shadow → يجب أن يكون عادياً"          │
│  (لأنه يحدث كثيراً معاً)                                   │
│                                                             │
│  ولكن الحقيقة:                                              │
│  المهاجم زرع backdoor في nginx                              │
│  → nginx يقرأ shadow بسبب الـ backdoor لا بسبب وظيفته       │
│  → الـ confounders: الـ backdoor (سبب مخفي)                 │
│                                                             │
│  ─────────────────────────────────────────────────────────  │
│                                                             │
│  SENTINEL (سببية):                                         │
│  "إذا شغّلنا nginx نظيف (تدخل) — هل يقرأ shadow؟"        │
│  → لا! nginx النظيف لا يحتاج shadow                       │
│  → إذاً القراءة ليست سببية لوظيفة nginx                    │
│  → شيء آخر يسبّبها ← ALERT                                │
│                                                             │
└─────────────────────────────────────────────────────────────┘
```

## 2. سلّم السببية — Pearl's Ladder of Causation

Judea Pearl (الحائز على جائزة تورينغ 2011) صنّف الذكاء السببي في ثلاث طبقات. هذا السلّم هو الأساس النظري لـ SENTINEL:

```
┌─────────────────────────────────────────────────────────────┐
│                                                             │
│  الطبقة 3 — Counterfactual (التخيّل)     ← SENTINEL هنا   │
│  ═══════════════════════════════════                         │
│  السؤال: "لو لم يحدث X، هل كان Y سيحدث؟"                 │
│  القدرة: تخيّل عوالم بديلة لم تحدث                         │
│  مثال: "لو لم يقرأ nginx الـ shadow، هل كان سيرسل بيانات؟"│
│  من يملكها: البشر فقط (حتى الآن) + SENTINEL                │
│                                                             │
│  ▲                                                          │
│  │                                                          │
│  الطبقة 2 — Intervention (التدخل)                           │
│  ═══════════════════════════════                              │
│  السؤال: "إذا فعلت X، ماذا سيحدث لـ Y؟"                   │
│  القدرة: التدخل في العالم وتوقّع النتائج                    │
│  مثال: "إذا أوقفت nginx، هل تتوقف قراءة shadow؟"           │
│  الفرق عن الملاحظة: هنا أنت تتدخل، لا تراقب فقط           │
│  من يملكها: البشر + بعض الحيوانات                            │
│                                                             │
│  ▲                                                          │
│  │                                                          │
│  الطبقة 1 — Association (الملاحظة)    ← كل الأنظمة الحالية │
│  ═══════════════════════════════                              │
│  السؤال: "ماذا لاحظت؟ ما الأنماط في البيانات؟"             │
│  القدرة: اكتشاف ارتباطات إحصائية                            │
│  مثال: "nginx يقرأ shadow في 5% من الحالات"                 │
│  من يملكها: كل نماذج ML الحالية                              │
│                                                             │
└─────────────────────────────────────────────────────────────┘
```

### لماذا هذا السلّم مهم؟

```
Darktrace, CrowdStrike, Vectra, KAIROS, FLASH, MAGIC:
  كلهم يعملون في الطبقة 1 (Association)
  يرون أنماطاً ويقارنونها مع baseline
  ← المهاجم الذكي يجعل نمطه يبدو عادياً → يتهرب

SENTINEL:
  يعمل في الطبقة 3 (Counterfactual)
  يسأل "لماذا" و"ماذا لو"
  ← المهاجم لا يستطيع تغيير "لماذا" — السببية ثابتة
```

## 3. المتغيرات المربكة (Confounders) — العدو الخفي

### ما هو الـ Confounder؟

```
Confounder = متغير مخفي يؤثر على X و Y معاً
             فيبدو أن X يسبب Y — ولكنه لا يسببه

┌──────────────────────────────────────────────────────────┐
│                                                          │
│  المثال الكلاسيكي:                                       │
│                                                          │
│          ┌────────────┐                                   │
│          │  الحرارة   │ ← Confounder (مخفي)               │
│          └──┬─────┬───┘                                   │
│             │     │                                       │
│             ▼     ▼                                       │
│     ┌───────────┐  ┌──────────┐                           │
│     │ مثلجات   │  │  غرق    │                            │
│     └───────────┘  └──────────┘                           │
│             ↑                                             │
│     يبدو أن هناك علاقة ← ولكنها وهمية (spurious)         │
│                                                          │
│  ─────────────────────────────────────────────────────── │
│                                                          │
│  في الأمن السيبراني:                                     │
│                                                          │
│          ┌────────────┐                                   │
│          │  Backdoor  │ ← Confounder (مخفي)               │
│          └──┬─────┬───┘                                   │
│             │     │                                       │
│             ▼     ▼                                       │
│     ┌───────────┐  ┌──────────────┐                      │
│     │ nginx     │  │ قراءة shadow │                       │
│     │ يعمل     │  │              │                        │
│     └───────────┘  └──────────────┘                       │
│             ↑                                             │
│     النظام التقليدي يربط nginx بـ shadow ← خطأ!          │
│     الـ backdoor هو السبب الحقيقي                         │
│                                                          │
└──────────────────────────────────────────────────────────┘
```

### كيف يتعامل SENTINEL مع Confounders؟

الحل يأتي من Pearl — **Do-Calculus** — الذي يُزيل تأثير الـ confounders رياضياً:

```
بدل:  P(shadow_read | nginx_running)         ← ملاحظة (فيها confounders)
نحسب: P(shadow_read | do(nginx_running))     ← تدخل (بدون confounders)

الفرق:
  P(Y | X)      = "عندما نرى X، كم مرة نرى Y؟"
                  → يشمل تأثير الـ confounders
                  
  P(Y | do(X))  = "إذا أجبرنا X أن يحدث، كم مرة نرى Y؟"
                  → يُزيل تأثير الـ confounders تماماً
                  → لأننا نحن "فعلنا" X — لا شيء آخر أثّر عليه
```

# الجزء الثاني: الأدوات الرياضية — Pearl's Do-Calculus

## 4. عامل التدخل — do(X)

هذا هو الاختراع الأهم في تاريخ السببية. Pearl اخترعه عام 1995 وغيّر به مجال الذكاء الاصطناعي.

### التعريف البسيط:

```
P(Y | X = x)      يعني: "راقب X ولاحظ أنه x — ما احتمال Y؟"
P(Y | do(X = x))  يعني: "ادخل واجعل X = x قسراً — ما احتمال Y؟"

الفرق الجوهري:
  عندما تراقب: X قد يكون x بسبب confounder
  عندما تتدخل: أنت كسرت كل العلاقات التي تؤثر على X
               → X = x فقط لأنك أنت قررت ذلك
               → أي تغيير في Y بعد ذلك = بسبب X فعلاً
```

### مثال عملي في SENTINEL:

```
┌─────────────────────────────────────────────────────────────┐
│                                                             │
│  السيناريو: nginx يقرأ /etc/shadow                         │
│                                                             │
│  ─── الملاحظة (Observation) ───                             │
│  P(shadow_read | nginx_running)                             │
│  = "من بين كل المرات اللي شغلنا فيها nginx،                │
│     كم مرة قرأ shadow؟"                                     │
│  = 0.15 (15%)                                               │
│                                                             │
│  ←  هذا مرتفع! ولكن هل nginx هو السبب؟                     │
│     ربما الـ backdoor (confounder) هو السبب                 │
│     وnginx يعمل بالصدفة في نفس الوقت                       │
│                                                             │
│  ─── التدخل (Intervention) ───                              │
│  P(shadow_read | do(nginx_start))                           │
│  = "إذا شغّلنا nginx نظيف بأنفسنا (تدخل)                  │
│     — على خادم نظيف — هل يقرأ shadow؟"                      │
│  = 0.001 (0.1%)                                             │
│                                                             │
│  ←  منخفض جداً! nginx النظيف لا يقرأ shadow                │
│     إذاً الـ 15% في الملاحظة كانت بسبب الـ backdoor         │
│     لا بسبب nginx نفسه                                      │
│                                                             │
│  الفرق = 0.15 - 0.001 = 0.149                              │
│  هذا الفرق = تأثير الـ confounder (الـ backdoor)            │
│  = الفجوة السببية ← حجم المشكلة الحقيقية                   │
│                                                             │
└─────────────────────────────────────────────────────────────┘
```

## 5. كيف نحسب do(X) عملياً — بدون خادم مختبر؟

المشكلة: لا يمكننا فعلاً تشغيل nginx نظيف في كل مرة نريد اختبار سببية.

الحل: ثلاث طرق رياضية تحسب do(X) من البيانات المتاحة:

### الطريقة 1 — Back-Door Adjustment (عندما نعرف الـ confounders):

$$P(Y | do(X)) = \sum_{z} P(Y | X, Z=z) \cdot P(Z=z)$$

```
المعنى بالعربي:
  إذا عرفنا كل الـ confounders Z — نقدر نحسب do(X)
  بأننا "نتحكم" في Z ونثبّته ثم نحسب تأثير X على Y
  
مثال:
  X = nginx_running
  Y = shadow_read
  Z = {backdoor_present, cron_job, admin_script}  ← confounders
  
  P(shadow | do(nginx)) 
  = Σ_z P(shadow | nginx, Z=z) × P(Z=z)
  = P(shadow | nginx, no_backdoor) × P(no_backdoor)
    + P(shadow | nginx, backdoor) × P(backdoor)
  = 0.001 × 0.95 + 0.90 × 0.05
  = 0.00095 + 0.045
  = 0.046
  
  ← بدون backdoor: 0.1% فقط = nginx لا يسبب shadow_read
  ← مع backdoor: 90% = الـ backdoor هو السبب
```

**المشكلة**: في kernel حقيقي، لا نعرف كل الـ confounders! (kernel scheduler, cgroups, race conditions...)

### الطريقة 2 — Front-Door Adjustment (عندما لا نعرف الـ confounders):

$$P(Y | do(X)) = \sum_{m} P(m | X) \cdot \sum_{x'} P(Y | m, X=x') \cdot P(X=x')$$

```
المعنى بالعربي:
  لا نحتاج معرفة الـ confounders!
  نحتاج فقط معرفة "الوسطاء" M (mediators) — 
  الأحداث التي تحدث بين X و Y

مثال:
  X = nginx_running
  M = syscalls الوسيطة (open, read, write, connect)
  Y = shadow_read
  
  الخطوة 1: P(m | X)
    "ما الـ syscalls التي يُصدرها nginx عادةً؟"
    P(open_normal_files | nginx) = 0.95
    P(open_sensitive_files | nginx) = 0.001
    P(exec_shell | nginx) = 0.0001
    
  الخطوة 2: P(Y | m)  
    "ما احتمال قراءة shadow بعد كل syscall?"
    P(shadow | open_normal) = 0.0
    P(shadow | open_sensitive) = 0.8
    P(shadow | exec_shell) = 0.5
    
  النتيجة:
    P(shadow | do(nginx))
    = 0.95 × 0.0 + 0.001 × 0.8 + 0.0001 × 0.5
    = 0 + 0.0008 + 0.00005
    = 0.00085
    
  ← nginx سببياً يُنتج shadow_read بنسبة 0.085% فقط!
  ← أي قراءة shadow ≈ ليست بسبب nginx ← ALERT
```

**لماذا هذه الطريقة أفضل لـ SENTINEL:**

```
✅ لا تحتاج معرفة confounders (kernel معقد جداً)
✅ تحتاج فقط معرفة syscalls — وeBPF يرصدها كلها!  
✅ مُثبتة رياضياً (Pearl, 1995) — ليست تقديراً approximate
✅ قابلة للحساب في real-time
```

### الطريقة 3 — Instrumental Variables (عندما لا يوجد وسطاء واضحون):

```
نستخدم "أداة" Z تؤثر على X فقط (لا تؤثر مباشرة على Y)

في SENTINEL:
  Z = system boot (إعادة تشغيل)
  X = process behavior
  Y = suspicious activity
  
  الـ boot يؤثر على أي processes تعمل (X)
  ولكنه لا يسبب هجمات بنفسه (Y)
  → يمكن استخدامه كـ instrumental variable
  
هذه الطريقة أقل استخداماً في SENTINEL — نفضل Front-Door
```

## 6. التفكير المضاد (Counterfactual) — الطبقة الثالثة من سلّم Pearl

هذا هو أعلى مستوى من الذكاء السببي. السؤال:

> **"في هذا العالم بالذات، لو لم يحدث X، هل كان Y سيحدث؟"**

### الفرق عن التدخل:

```
التدخل (do):     "بشكل عام، إذا شغّلنا nginx، هل يقرأ shadow؟"
                  → إجابة عامة عن كل nginx في كل وقت

المضاد (CF):     "في هذه الحالة بالذات، هذا الـ nginx في هذا الخادم
                  الساعة 3:47 صباحاً — لو لم يقرأ shadow،
                  هل كان سيرسل بيانات لـ 45.33.32.156?"
                  → إجابة محددة عن هذا الحدث بالذات
```

### المعادلة الرسمية:

$$CF(Y | do(\neg X)) = \sum_{z} P(Y | X=0, Z=z) \cdot P(Z=z | X=1)$$

### شرح المعادلة خطوة بخطوة:

```
┌─────────────────────────────────────────────────────────────┐
│                                                             │
│  CF(Y | do(¬X))                                             │
│                                                             │
│  المعنى: "في العالم البديل حيث X لم يحدث، ما احتمال Y؟"   │
│                                                             │
│  = Σ_z  P(Y | X=0, Z=z)  ×  P(Z=z | X=1)                  │
│         ─────────────────     ──────────────                │
│         │                     │                             │
│         │                     └─ "ما قيم Z في العالم        │
│         │                        الحقيقي حيث X حدث؟"       │
│         │                        نأخذ Z من الواقع            │
│         │                                                   │
│         └─ "في هذا السياق (Z)،                              │
│            لو X لم يحدث،                                    │
│            ما احتمال Y؟"                                    │
│            نحسب Y في العالم البديل                           │
│                                                             │
│  ─────────────────────────────────────────────────────────  │
│                                                             │
│  بالعربي:                                                   │
│  1. انظر للعالم الحقيقي: X حدث, Z كانت بقيم معينة         │
│  2. تخيّل عالماً بديلاً: نفس Z ولكن X لم يحدث              │
│  3. في هذا العالم البديل: هل Y لا يزال يحدث؟               │
│  4. إذا نعم → X لم يكن ضرورياً → ليس السبب الحقيقي        │
│  5. إذا لا → X كان ضرورياً → هو السبب الحقيقي             │
│                                                             │
└─────────────────────────────────────────────────────────────┘
```

### تطبيق على Mimicry Attack:

```
┌─────────────────────────────────────────────────────────────┐
│                                                             │
│  الهجوم:                                                    │
│  nginx → read(access.log) × 100  ← benign (ضجيج)           │
│  nginx → read(error.log)  × 50   ← benign (ضجيج)           │
│  nginx → read(/etc/shadow) × 1   ← الهجوم                  │
│  nginx → send(C2: 45.33.32.156)  ← exfiltration             │
│                                                             │
│  النظام التقليدي:                                           │
│  shadow_read = 1 من 151 قراءة = 0.66%                       │
│  "قراءات nginx متنوعة وshadow نسبة صغيرة → عادي"          │
│  ← MISS ✗                                                   │
│                                                             │
│  ────────────────────────────────────────────────────────── │
│                                                             │
│  SENTINEL — Counterfactual لكل edge:                        │
│                                                             │
│  اختبار 1: CF(send_C2 | do(¬ read_access_log))             │
│  "لو nginx لم يقرأ access.log — هل كان سيرسل لـ C2؟"      │
│                                                             │
│    العالم الحقيقي: access_log قُرئ + C2 حدث                 │
│    العالم البديل: access_log لم يُقرأ                       │
│    → هل send_C2 يتأثر؟ → لا!                               │
│    → access_log قراءة لملف log لا يحتويه C2 packet          │
│    → CF ≈ P(send_C2) ← نفس الاحتمال                        │
│    → النتيجة: access_log ليس سبباً ← NOISE                  │
│                                                             │
│  اختبار 2: CF(send_C2 | do(¬ read_shadow))                  │
│  "لو nginx لم يقرأ shadow — هل كان سيرسل لـ C2؟"           │
│                                                             │
│    العالم الحقيقي: shadow قُرئ + C2 حدث                     │
│    العالم البديل: shadow لم يُقرأ                            │
│    → هل send_C2 يتأثر؟ → نعم!                              │
│    → بدون shadow لا يوجد بيانات لإرسالها                    │
│    → CF ≈ 0 ← الاحتمال ينهار                                │
│    → النتيجة: shadow_read هو السبب الحقيقي ← ATTACK         │
│                                                             │
│  اختبار 3: CF(send_C2 | do(¬ read_error_log))              │
│  → CF ≈ P(send_C2) ← لا تأثير ← NOISE                      │
│                                                             │
│  ────────────────────────────────────────────────────────── │
│                                                             │
│  الملخص:                                                    │
│  من 151 قراءة:                                              │
│  → 150 قراءة = noise (كشفها CF)                             │
│  → 1 قراءة = السبب الحقيقي (shadow → C2)                   │
│  Mimicry كُشف رياضياً ← الضجيج لا يغيّر السببية           │
│                                                             │
└─────────────────────────────────────────────────────────────┘
```

# الجزء الثالث: كيف يُبنى النموذج السببي في SENTINEL

## 7. الخطوة الأولى — تحويل كل حدث إلى Causal Triple

كل syscall من eBPF يُحوَّل لهذا الشكل:

$$\tau = (s, a, o, t, c, d)$$

```
┌─────────────────────────────────────────────────────────────┐
│                    Causal Triple                            │
│                                                             │
│  s = Subject     من فعل الفعل؟          nginx (PID 1234)   │
│  a = Action      ماذا فعل؟              read               │
│  o = Object      على ماذا؟              /etc/shadow        │
│  t = Timestamp   متى؟                   1713045000.123 ns  │
│  c = Context     السياق السببي:                             │
│                  من أعطى الأمر؟          parent = bash      │
│                  بأي صلاحيات؟            uid = root         │
│                  في أي بيئة؟             namespace = default│
│  d = Depth       كم بعيد عن مصدر القرار؟ depth = 3          │
│                                                             │
│  ─────────────────────────────────────────────────────────  │
│                                                             │
│  لماذا الـ Context مهم؟                                     │
│                                                             │
│  بدون context:                                              │
│    (nginx, read, shadow) ← لا نعرف من أمر بذلك              │
│    قد يكون admin يفحص يدوياً ← benign                       │
│    قد يكون backdoor ← malicious                             │
│    لا يمكن التمييز!                                         │
│                                                             │
│  مع context:                                                │
│    (nginx, read, shadow, {parent=systemd, uid=www}) ← غريب │
│    (nginx, read, shadow, {parent=bash, uid=root}) ← خطير   │
│    (admin_tool, read, shadow, {parent=sshd, uid=admin}) ← OK│
│    الآن يمكن التمييز!                                       │
│                                                             │
│  ─────────────────────────────────────────────────────────  │
│                                                             │
│  لماذا الـ Depth مهم؟                                       │
│                                                             │
│  depth=0: المستخدم مباشرة طلب الفعل (إدخال لوحة المفاتيح)  │
│  depth=1: البرنامج استجاب لأمر المستخدم                     │
│  depth=2: برنامج آخر استُدعي بسبب البرنامج الأول            │
│  depth=5: سلسلة من 5 برامج ← بعيد جداً عن مصدر القرار      │
│                                                             │
│  nginx يقرأ shadow بـ depth=1 ← مباشر ← مريب               │
│  nginx يقرأ shadow بـ depth=5 ← عبر سلسلة طويلة ← أخطر!    │
│  لأن العمق يشير إلى محاولة إخفاء                            │
│                                                             │
└─────────────────────────────────────────────────────────────┘
```

## 8. الخطوة الثانية — بناء الرسم البياني السببي (CIG)

### التعريف:

$$G_{CIG} = (V, E, \phi, \psi, \kappa)$$

```
V = العقد (nodes) — كل كيان في النظام
    process: nginx, bash, python, sshd
    file: /etc/shadow, /var/log/access.log
    socket: 192.168.1.1:80, 45.33.32.156:443

E = الأضلاع (edges) — العلاقات السببية بين الكيانات
    nginx → read → access.log
    bash → exec → wget
    wget → connect → evil.com

φ(v) = النية المستنتجة لكل عقدة
    φ(nginx) = benign (0.95)
    φ(bash) = unknown (0.5)
    φ(wget_from_bash) = recon (0.7)

ψ(e) = وزن السببية لكل ضلع — "كم هذا الحدث سببي حقاً؟"
    ψ(nginx → access.log) = 0.95 (طبيعي جداً → وزن عالي)
    ψ(nginx → shadow) = 0.05 (غير طبيعي → وزن منخفض)

κ(v) = الفضاء المضاد — "ماذا لو لم يوجد هذا الكيان؟"
    κ(wget) = "بدون wget، لا download → لا payload"
    κ(access.log) = "بدون access.log، nginx يعمل بشكل عادي"
```

### الفرق البصري بين Provenance Graph و CIG:

```
┌─────────────────────────────────────────────────────────────┐

│                                                             │
```

## 9. الخطوة الثالثة — حساب وزن السببية ψ(e)

هذا هو القلب الرياضي للنموذج. كل ضلع في الـ CIG يحمل وزناً يقيس **"كم هذه العلاقة سببية حقاً؟"**

### المعادلة — Gated Combination:

$$\psi(e_{ij}) = \underbrace{P(v_j | do(v_i))}_{\text{الاحتمال السببي}} \cdot \underbrace{\sigma\Big(\beta \cdot \text{decay}(\Delta t) + \gamma \cdot \text{sem}(v_i, v_j) - b\Big)}_{\text{البوابة: زمنية + دلالية}}$$

### شرح كل جزء بالتفصيل:

```
┌─────────────────────────────────────────────────────────────┐
│                                                             │
│  الجزء 1: P(v_j | do(v_i)) — الاحتمال السببي التدخلي      │
│  ═══════════════════════════════════════════════════         │
│                                                             │
│  "إذا أجبرنا v_i أن يحدث — ما احتمال v_j؟"               │
│                                                             │
│  يُحسب عبر Front-Door Adjustment:                          │
│  P(v_j | do(v_i)) = Σ_m P(v_j | m) × P(m | v_i)          │
│                                                             │
│  مثال:                                                      │
│  v_i = nginx, v_j = shadow_read                             │
│  m = {open_sensitive, exec_shell, ...}                      │
│                                                             │
│  P(shadow | do(nginx))                                      │
│  = P(shadow | open_sensitive) × P(open_sensitive | nginx)   │
│    + P(shadow | exec_shell) × P(exec_shell | nginx)        │
│  = 0.8 × 0.001 + 0.5 × 0.0001                              │
│  = 0.00085 ← منخفض جداً                                     │
│                                                             │
│  ─────────────────────────────────────────────────────────  │
│                                                             │
│  الجزء 2: البوابة (Gate) — σ(β·decay + γ·sem - b)          │
│  ═══════════════════════════════════════════════════         │
│                                                             │
│  هذه "بوابة" تُضيّق أو تُوسّع الوزن السببي بناءً على:     │
│                                                             │
│  (أ) temporal_decay — الانحلال الزمني:                       │
│      decay(Δt) = e^(-λ·Δt)                                  │
│                                                             │
│      Δt صغير (1ms):  decay = 0.999 ← قريبان زمنياً         │
│                       → البوابة تفتح (وزن عالي)              │
│      Δt كبير (1min): decay = 0.001 ← بعيدان زمنياً          │
│                       → البوابة تُغلق (وزن منخفض)            │
│                                                             │
│      المعنى: الأحداث القريبة زمنياً أكثر احتمالاً           │
│      أن تكون سببية                                          │
│                                                             │
│  (ب) semantic_distance — المسافة الدلالية:                   │
│      sem(v_i, v_j) = cos(embedding_i, embedding_j)          │
│                      × 𝟙[¬axiom_violated]                   │
│                                                             │
│      sem(nginx, access.log) = +0.95 ← منطقيان معاً          │
│                                → البوابة تفتح                │
│      sem(nginx, shadow) = -0.80 ← غير منطقيين               │
│                           → البوابة تُغلق                    │
│      sem(nginx, bash) = -∞ ← مستحيل (axiom violation)       │
│                         → البوابة مغلقة تماماً               │
│                                                             │
│  (ج) الـ sigmoid σ يحوّل كل شيء لـ [0, 1]:                 │
│      σ(x) = 1/(1+e^(-x))                                   │
│                                                             │
│      مدخل موجب كبير → σ ≈ 1.0 → البوابة مفتوحة             │
│      مدخل صفر       → σ = 0.5 → نصف مفتوحة                 │
│      مدخل سالب كبير → σ ≈ 0.0 → البوابة مغلقة              │
│                                                             │
│  ─────────────────────────────────────────────────────────  │
│                                                             │
│  لماذا Gated وليس Linear؟                                  │
│  ═══════════════════════════                                 │
│                                                             │
│  Linear: ψ = α·P(do) + β·decay + γ·sem                     │
│                                                             │
│  مشكلة: sem(nginx, shadow) = -0.8                           │
│  ← يُضاف كعدد سالب صغير ← لا يُلغي الوزن كلياً           │
│  ← P(do) العالي لا يزال يرفع ψ ← خطأ!                     │
│                                                             │
│  Gated: ψ = P(do) × σ(decay + sem)                         │
│                                                             │
│  ← sem = -0.8 يجعل σ ≈ 0.3                                 │
│  ← P(do) × 0.3 ← الوزن مخنوق!                             │
│  ← حتى لو P(do) مرتفع — البوابة تمنعه                     │
│  ← هذا أصح: إذا الـ semantics تقول "مستحيل"                │
│     فلا يهم ما يقوله الاحتمال                               │
│                                                             │
└─────────────────────────────────────────────────────────────┘
```

### مثال عددي كامل:

```
┌─────────────────────────────────────────────────────────────┐
│  Edge: nginx → read(/etc/shadow) في t=1000                 │
├─────────────────────────────────────────────────────────────┤
│                                                             │
│  الخطوة 1: P(shadow_read | do(nginx))                      │
│  ─────────────────────────────────────                      │
│  Front-Door: Σ P(shadow|m) × P(m|nginx)                    │
│    m=open_file:     0.01 × 0.90 = 0.009                    │
│    m=open_sensitive: 0.80 × 0.001 = 0.0008                  │
│    m=exec_shell:    0.50 × 0.0001 = 0.00005                │
│    Total = 0.00985 ≈ 0.01                                   │
│                                                             │
│  الخطوة 2: decay(Δt)                                       │
│  ─────────────────────                                      │
│  الحدث السابق في t=999 → Δt = 1ms                         │
│  decay = e^(-0.001 × 1) = 0.999                            │
│                                                             │
│  الخطوة 3: sem(nginx, shadow)                               │
│  ─────────────────────────────                               │
│  cos(embedding_nginx, embedding_shadow) = -0.7              │
│  axiom_violated? → ليس Universal ولكنه Contextual          │
│  𝟙[¬axiom] = 1 (لم ينتهك axiom مطلق)                      │
│  sem = -0.7 × 1 = -0.7                                     │
│                                                             │
│  الخطوة 4: البوابة                                          │
│  ─────────────────                                          │
│  gate_input = β×decay + γ×sem - b                          │
│             = 0.5×0.999 + 0.5×(-0.7) - 0.3                 │
│             = 0.4995 - 0.35 - 0.3                           │
│             = -0.1505                                       │
│  gate = σ(-0.1505) = 0.462                                  │
│                                                             │
│  الخطوة 5: الوزن النهائي                                    │
│  ───────────────────────                                     │
│  ψ = P(do) × gate                                           │
│    = 0.01 × 0.462                                           │
│    = 0.00462                                                │
│                                                             │
│  ψ = 0.005 ← منخفض جداً!                                    │
│                                                             │
│  المعنى: هذا الحدث (nginx→shadow) له وزن سببي 0.5% فقط    │
│  → ليس طبيعياً → مشبوه → يُرسل للتحليل العميق              │
│                                                             │
│  للمقارنة:                                                  │
│  ψ(nginx → access.log) = 0.95 × σ(0.5+0.475-0.3)          │
│                        = 0.95 × σ(0.675)                    │
│                        = 0.95 × 0.66                        │
│                        = 0.63 ← طبيعي ✓                     │
│                                                             │
└─────────────────────────────────────────────────────────────┘
```

## 10. الخطوة الرابعة — استنتاج النية (Intent Inference)

### السؤال المركزي:

> **"بناءً على السلسلة السببية لهذا الكيان — ما نيته؟"**

### فضاء النوايا — Hierarchical (هرمي):

```
┌─────────────────────────────────────────────────────────────┐
│                                                             │
│  لماذا هرمي وليس مسطح؟                                     │
│                                                             │
│  الفضاء المسطح: {benign, recon, exfil, escalation, ...}    │
│  المشكلة: 9 خيارات دفعة واحدة = بطيء + أخطاء               │
│                                                             │
│  الفضاء الهرمي: سؤال تلو سؤال                              │
│                                                             │
│  السؤال 1 (سريع جداً):                                      │
│    benign أم malicious؟                                     │
│    ← إذا benign بثقة > 99% → ALLOW فوراً (لا حاجة لسؤال 2)│
│    ← يوفر 95% من وقت الحساب!                               │
│                                                             │
│  السؤال 2 (إذا suspicious):                                 │
│    pre-attack, active-attack, أم post-attack؟               │
│    ← يحدد إلحاح الاستجابة                                  │
│                                                             │
│  السؤال 3 (للتصنيف الدقيق):                                 │
│    أي نوع بالضبط؟ recon, exfil, lateral, c2, ...            │
│    ← للتقرير والتوثيق                                       │
│                                                             │
│  الفائدة: 95% من الأحداث تُحل في السؤال 1                  │
│           4% في السؤال 2                                     │
│           1% فقط يحتاج السؤال 3 (الأعمق)                    │
│                                                             │
└─────────────────────────────────────────────────────────────┘
```

### المعادلة — Constrained Inference:

$$\mathcal{I}(v) = \arg\max_{i \in \mathcal{C}} P(i | \text{chain}(v)) \cdot \mathbb{1}[\neg \text{axiom\_violated}(v, i)]$$

### شرح بالتفصيل:

```
┌─────────────────────────────────────────────────────────────┐
│                                                             │
│  P(i | chain(v)):                                           │
│  "بناءً على كل السلسلة السببية لهذا الكيان،                │
│   ما احتمال أن نيته هي i؟"                                  │
│                                                             │
│  chain(v) = كل الأحداث المرتبطة سببياً بـ v                │
│  ليس فقط آخر حدث — بل كل التاريخ السببي                   │
│  بما فيه الـ tattoos من أسابيع سابقة!                       │
│                                                             │
│  مثال:                                                      │
│  chain(hidden_script) = [                                   │
│    php-fpm wrote hidden_script (t=0),                       │
│    php-fpm executed hidden_script (t=1ms),                  │
│    hidden_script read /etc/passwd (t=5ms),                  │
│    hidden_script connected to 45.33.32.156 (t=10ms),        │
│    tattoo from 2 weeks ago: php-fpm had suspicious write    │
│  ]                                                          │
│                                                             │
│  P(benign | chain) = 0.02                                   │
│  P(exfil | chain) = 0.71                                    │
│  P(recon | chain) = 0.12                                    │
│  P(persist | chain) = 0.08                                  │
│  P(c2 | chain) = 0.05                                       │
│  P(other | chain) = 0.02                                    │
│                                                             │
│  ─────────────────────────────────────────────────────────  │
│                                                             │
│  × 𝟙[¬ axiom_violated(v, i)]:                              │
│  "هل هذه النية منطقياً ممكنة؟"                              │
│                                                             │
│  𝟙 = indicator function = 0 أو 1                           │
│                                                             │
│  مثال:                                                      │
│  هل "nginx → bash" يمكن أن يكون benign؟                    │
│  axiom يقول: web_server ≠ spawn(shell)                      │
│  → 𝟙[¬axiom_violated(nginx_bash, benign)] = 0              │
│  → P(benign) × 0 = 0                                       │
│  → مستحيل رياضياً أن يكون benign                            │
│                                                             │
│  لماذا هذا ثوري؟                                            │
│  لأن 0 × أي شيء = 0                                         │
│  حتى لو المهاجم سمّم الـ training data لسنوات              │
│  وجعل P(benign | nginx→bash) = 0.99                        │
│  → 0.99 × 0 = 0 ← لا يزال مستحيلاً!                       │
│                                                             │
│  هذا هو الفرق بين Hard Constraint و Soft Constraint:       │
│  Hard: 0 × anything = 0 ← لا يمكن التغلب عليه              │
│  Soft: 0.01 × 0.99 = 0.0099 ← يمكن رفعه بالـ poisoning    │
│                                                             │
└─────────────────────────────────────────────────────────────┘
```

## 11. الخطوة الخامسة — Causal Entropy (قياس الشك)

### لماذا لا يكفي Confidence العادي؟

```
┌─────────────────────────────────────────────────────────────┐
│                                                             │
│  الحالة A:                                                  │
│  P(benign) = 0.45                                           │
│  P(exfil)  = 0.55                                           │
│  Confidence = max = 0.55 ← "ربما exfil"                    │
│  Entropy = -(0.45×log0.45 + 0.55×log0.55)                   │
│          = 0.99 bits ← شك متوسط                             │
│                                                             │
│  الحالة B:                                                  │
│  P(benign) = 0.45                                           │
│  P(recon)  = 0.15                                           │
│  P(exfil)  = 0.15                                           │
│  P(lateral)= 0.10                                           │
│  P(c2)     = 0.10                                           │
│  P(persist)= 0.05                                           │
│  Confidence = max = 0.45 ← "ربما benign" ← أقل!           │
│  Entropy = 2.32 bits ← شك عالي جداً!                       │
│                                                             │
│  ─────────────────────────────────────────────────────────  │
│                                                             │
│  المفارقة:                                                  │
│  Confidence تقول: B أقل خطراً (0.45 benign vs 0.55 exfil)  │
│  Entropy تقول: B أخطر بكثير! (2.32 vs 0.99)               │
│                                                             │
│  لماذا Entropy محقّة؟                                       │
│  في الحالة B: النموذج "مشتت" بين 6 نوايا مختلفة            │
│  4 منها خبيثة (recon + exfil + lateral + c2)               │
│  هذا يشير لهجوم متعدد المراحل (multi-stage attack)!       │
│  والـ Confidence العادي لا يكشف هذا!                        │
│                                                             │
└─────────────────────────────────────────────────────────────┘
```

### المعادلة:

$$H_{causal}(v) = -\sum_{i \in \mathcal{C}} P(i | \text{chain}(v)) \cdot \log_2 P(i | \text{chain}(v))$$

### كيف يُستخدم:

```
H < 0.5 bits   → شك منخفض → النموذج متأكد
                  → تصرف فوراً (kill أو allow)

0.5 ≤ H < 1.5  → شك متوسط → يحتاج تحليل أعمق
                  → Do-Calculus + Counterfactual check

H ≥ 1.5 bits   → شك عالي → النموذج مشتت
                  → DECEPTION MODE
                  → اصطد المهاجم واجعله يكشف نيته
                  → كلما كشف أكثر ← H تنخفض ← نفهم أكثر
```

## 12. الخطوة السادسة — GNN مع Causal Attention

### لماذا نحتاج GNN أصلاً؟

```
┌─────────────────────────────────────────────────────────────┐
│                                                             │
│  المشكلة: لدينا graph به آلاف العقد وملايين الأضلاع.       │
│  كيف نحسب P(intent | chain) لكل عقدة بكفاءة؟               │
│                                                             │
│  الحل: GNN (Graph Neural Network)                           │
│                                                             │
│  GNN يعمل هكذا:                                             │
│    1. كل عقدة تبدأ بـ feature vector (اسمها، نوعها، ...)    │
│    2. كل عقدة "تسأل" جيرانها: "من أنت وماذا تفعل؟"        │
│    3. كل عقدة تجمع معلومات من جيرانها                       │
│    4. تُحدّث embedding الخاص بها                            │
│    5. تكرر الخطوات 2-4 عدة مرات (layers)                    │
│    6. بعد عدة جولات: كل عقدة "تفهم" سياقها في الـ graph     │
│                                                             │
│  المخرج: embedding vector لكل عقدة                          │
│  يُستخدم لحساب P(intent | chain)                            │
│                                                             │
└─────────────────────────────────────────────────────────────┘
```

### المشكلة مع GNN العادي — Oversmoothing:

```
┌─────────────────────────────────────────────────────────────┐
│                                                             │
│  بعد 4 طبقات GNN — كل العقد تتشابه!                        │
│                                                             │
│  لماذا؟                                                     │
│  لأن كل عقدة جمعت معلومات من كل الـ graph تقريباً          │
│  → كلهم يعرفون نفس المعلومات                                │
│  → embeddings متشابهة ← لا يمكن التمييز!                    │
│                                                             │
│  التأثير على الأمن:                                         │
│  nginx (benign) و hidden_script (malicious)                  │
│  بعد 4 طبقات: embedding_nginx ≈ embedding_hidden            │
│  ← لا يمكن التمييز بينهما!                                  │
│  ← malicious يفلت!                                          │
│                                                             │
└─────────────────────────────────────────────────────────────┘
```

### الحل — Causal Attention:

```
GNN العادي:
  كل جار يساهم بالتساوي في embedding العقدة
  nginx يأخذ معلومات من access.log و shadow و bash بالتساوي!
  ← يتلوث بمعلومات "خاطئة"

SENTINEL — Causal Attention:
  كل جار يساهم حسب الوزن السببي ψ
  nginx يأخذ:
    من access.log: 95% (ψ = 0.63) ← طبيعي → يساهم كثيراً
    من shadow:     5% (ψ = 0.005) ← غير طبيعي → لا يساهم
    من bash:       0% (ψ = 0.00) ← مستحيل → لا يساهم أبداً
  
  ← embedding nginx يبقى "نظيفاً" = يعكس وظيفته الحقيقية
  ← shadow لا "يلوّث" nginx → يمكن التمييز بسهولة
  ← Oversmoothing SOLVED!
```

### المعادلة — Causal Attention:

$$\alpha_{ij}^{causal} = \frac{\exp\Big(\psi(e_{ij}) \cdot \mathbb{1}[\neg\text{axiom}(i,j)]\Big)}{\sum_{k \in \mathcal{N}(i)} \exp\Big(\psi(e_{ik})\Big)}$$

```
α_ij = "كم يجب أن يستمع node i لـ node j"

GNN العادي:  α = exp(sim(h_i, h_j)) / Σ exp(sim)
             ← يعتمد على تشابه الـ embeddings (إحصائي)

SENTINEL:    α = exp(ψ(e_ij) × 𝟙[¬axiom]) / Σ exp(ψ)
             ← يعتمد على الوزن السببي (سببي)
             ← axiom violation → α = 0 تماماً
```

### Multi-Head — أربعة أنواع انتباه:

```
┌─────────────────────────────────────────────────────────────┐
│                                                             │
│  Head 1 — Causal Strength:                                  │
│    "من الجيران الأكثر ارتباطاً سببياً؟"                     │
│    α¹ = softmax(ψ(e))                                       │
│    يكتشف: attack chains (سلاسل الهجوم)                     │
│                                                             │
│    مثال: bash→wget→payload→shadow→C2                        │
│    كل edge له ψ عالي → سلسلة واضحة                         │
│                                                             │
│  Head 2 — Temporal Proximity:                               │
│    "من الجيران الأقرب زمنياً؟"                               │
│    α² = softmax(decay(Δt))                                  │
│    يكتشف: rapid exploitation (هجوم سريع)                   │
│                                                             │
│    مثال: exec→read→send في 50ms = هجوم آلي                  │
│                                                             │
│  Head 3 — Axiom Violation:                                  │
│    "من الجيران الأكثر انتهاكاً للقواعد؟"                    │
│    α³ = softmax(violation_score(i,j))                       │
│    يكتشف: impossible behaviors (سلوك مستحيل)               │
│                                                             │
│    مثال: database → exec(curl) = axiom violation            │
│                                                             │
│  Head 4 — Counterfactual Necessity:                         │
│    "من الجيران الذين لا يمكن حذفهم دون تغيير النتيجة؟"    │
│    α⁴ = softmax(CF_necessity(e))                            │
│    يكتشف: causal backbone (العمود الفقري السببي)           │
│                                                             │
│    مثال: بدون shadow_read → لا exfil                        │
│    → shadow_read هو الـ backbone                             │
│                                                             │
│  ─────────────────────────────────────────────────────────  │
│                                                             │
│  الدمج:                                                     │
│  α_final = w₁·α¹ + w₂·α² + w₃·α³ + w₄·α⁴                 │
│                                                             │
│  الأوزان w₁...w₄ تُتعلَّم تلقائياً                        │
│  النظام يعرف متى يركّز على أي نوع                          │
│                                                             │
└─────────────────────────────────────────────────────────────┘
```
